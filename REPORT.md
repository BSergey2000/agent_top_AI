- задан предел длины — 150 слов;

**Анализ поведения:**

- **Типы проверяет FastMCP до вызова функции.** Строка `"3"` приводится к числу, `"abc"`, дробное `1.5` и пропущенный аргумент отклоняются с ошибкой валидации. Обратное приведение не делается: число `12345` вместо строки `city` тоже отклонено.
- **Большие и отрицательные числа складываются точно:** в Python целые числа не ограничены по разрядности.
- **API Open-Meteo нечувствителен к регистру:** `Paris`, `PARIS` и `paris` дают один и тот же город. Кириллица тоже работает.
- **Несуществующий город — это не ошибка HTTP.** Геокодер отвечает успешно, но без поля `results`; сервер превращает это в понятную ошибку инструмента.
- **Погода стоит двух сетевых запросов** (геокодирование, затем прогноз) — от 0,8 с до нескольких секунд против 3 мс у `add`. Пустой город отклоняется за 10–15 мс, без обращения к сети.
- **Сеть ненадёжна.** В одном из прогонов запрос к геокодеру оборвался с ошибкой соединения. После этого в `get_weather` добавлен повтор запроса, в следующих прогонах сбой не повторялся.

## 4–5. Transport протоколы

Оба режима проверены одним и тем же замером: подключение с `initialize`, затем 30 вызовов `add` подряд. Сервер и клиент — на одной машине.

| Критерий | stdio | streamable-http |
|--------|--------|--------|
| способ соединения | Клиент сам запускает сервер дочерним процессом и обменивается с ним JSON-RPC сообщениями через stdin/stdout | Сервер — отдельный процесс; клиент шлёт HTTP POST на `http://127.0.0.1:8000/mcp`, ответ приходит обычным JSON или потоком SSE |
| где используется | Локальные интеграции: IDE, десктопные приложения, CLI-агенты, MCP Inspector в режиме `make mcp_stdio` | Удалённые и общие серверы: веб-сервисы, облако, один сервер на команду |
| масштабируемость | Один клиент — один процесс сервера; подключиться к уже запущенному серверу второй клиент не может | Много клиентов на один сервер (проверено: два клиента одновременно получили ответы `2` и `4`); можно ставить за балансировщик |
| задержка | Подключение 1526 мс (запуск процесса Python), вызов — медиана 2.6 мс (2.24–5.45) | Подключение 53 мс (сервер уже работает), вызов — медиана 16.57 мс (14.89–46.93) |

**Вывод:** у stdio дорогой старт и дешёвый вызов, у streamable-http — наоборот. Набор инструментов, prompt и ресурсов в обоих режимах одинаков: транспорт меняет только способ доставки сообщений.

## 6. Модификация сервера

Все изменения — в [mcp-server.py](mcp-server.py).

- **Новый tool `convert_temperature`.** Переводит температуру между шкалами Цельсия, Фаренгейта и Кельвина. Принимает обозначения `C`/`F`/`K`, полные названия и знак градуса.
- **Новый resource `info-excursion://Yekaterinburg-trips`.** Экскурсии в Екатеринбурге, файл [src/data/yekaterinburg_trips.md](src/data/yekaterinburg_trips.md).
- **Обработка ошибок API в `get_weather`.** Таймаут 10 с, один повтор при сбое сети, отдельные сообщения для таймаута, отсутствия соединения, ошибки HTTP, ответа не в JSON и ответа без погоды. Раньше любой такой сбой ронял инструмент с трассировкой.
- **Проверка входных данных.** Пустой город, неизвестная шкала и температура ниже абсолютного нуля отклоняются с понятным текстом через `ToolError`.
- **Ошибки ресурсов.** Отсутствующий файл ресурса даёт `ResourceError` с именем файла.
- **Пути к файлам** считаются от расположения `mcp-server.py`, поэтому сервер можно запускать из любой папки.

В ответ `get_weather` добавлены найденный город и страна (`Погода в Париж, Франция: …`), чтобы было видно, какой именно город выбрал геокодер.

## 7. Анализ

### 1. Чем отличаются prompt, tool и resource?

| | Prompt | Tool | Resource |
|---|--------|------|----------|
| Что это | Шаблон инструкции с параметрами | Функция с типизированными аргументами | Данные, доступные по URI |
| Кто решает, когда использовать | Пользователь или приложение | Модель | Приложение-клиент |
| Что возвращает | Готовые сообщения для модели | Результат выполнения | Содержимое (текст, файл) |
| Побочные эффекты | Нет | Возможны: запрос к API, запись | Нет, только чтение |
| Пример в работе | `explain_topic` | `add`, `get_weather`, `convert_temperature` | `info-excursion://Paris-trips` |

### 2. Когда лучше использовать каждый из них?

- **Prompt** — когда есть повторяющаяся задача с проверенной формулировкой: её пишут один раз на сервере, и все клиенты получают одинаковое качество. Задание 1 показало, что от формулировки зависят язык, длина и поведение на некорректном вводе.
- **Tool** — когда нужно действие или свежие данные, которых нет в модели: вычисление, запрос к API, запись. Модель сама решает, вызывать ли его: в эксперименте с погодой в Париже она вызвала два инструмента подряд.
- **Resource** — когда модели нужен справочный контекст, который не требует вычислений: документы, справочники, образцы текста. Он дешевле инструмента (нет лишнего обращения к модели), но занимает место в контексте при каждом запросе.

### 3. Чем отличаются stdio и streamable-http?

Это два способа доставить одни и те же JSON-RPC сообщения. В stdio клиент запускает сервер как дочерний процесс и общается через стандартные потоки: настройка нулевая, сеть не нужна, но сервер живёт только вместе с одним клиентом. В streamable-http сервер работает самостоятельно и принимает HTTP-запросы: к нему подключаются многие клиенты, в том числе удалённые, но нужны адрес, порт и защита доступа. Замеры — в таблице раздела 4–5.

### 4. Какие преимущества MCP по сравнению с обычным API?

- **Один стандарт вместо отдельной интеграции под каждый сервис.** Агент в этой работе подключил два сервера — свой по stdio и удалённый сервер поиска Tavily по streamable-http — одинаковым кодом, не зная их внутреннего устройства.
- **Самоописание.** Сервер сам сообщает список инструментов, их описания и схемы аргументов; клиент узнаёт о новом инструменте без изменения кода. `convert_temperature` стал доступен агенту сразу после добавления на сервер.
- **Интерфейс рассчитан на модель.** Описания и схемы пишутся так, чтобы модель могла выбрать инструмент и заполнить аргументы; обычный API рассчитан на программиста, читающего документацию.
- **Не только функции.** Кроме вызовов есть prompt и resources — у обычного API нет стандартного способа передать шаблон инструкции или контекст.
- **Независимость от модели и клиента.** Тот же сервер работает с MCP Inspector, с агентом на LangChain и с любым другим MCP-клиентом.

Цена этого — дополнительный слой: для простого обращения одной программы к одному сервису обычный API проще и быстрее.

## 8. Работа с агентом MCP

Код агента — [main.py](main.py), [src/process.py](src/process.py) и [src/middleware.py](src/middleware.py).

- **8.1 Prompt.** Вход для агента берётся из MCP: `await client.get_prompt("main", "explain_topic", arguments={"topic": ...})`. Агент создаётся с этим prompt и двумя разными system_prompt (обычным и «строгим»).
- **8.2 Middleware.** В установленной версии LangChain 1.2.10 хуков `pre_ainvoke` / `post_ainvoke` нет; их роль выполняют `abefore_agent` и `aafter_agent`, а вызовы инструментов перехватывает `awrap_tool_call`. Сделаны три middleware:
  - `InputFilterMiddleware` — блокирует пустой, слишком длинный запрос и попытку подменить инструкции; маскирует почту, номер карты и API-ключ до отправки в модель;
  - `LoggingMiddleware` — логирует вход, каждый вызов инструмента с временем и итоговый ответ;
  - `ToolErrorMiddleware` — превращает исключение инструмента в сообщение об ошибке для модели. Без него ошибка «город не найден» обрывала бы работу агента.
- **8.3 Ресурсы.** `await client.get_resources("main")` возвращает все три ресурса; они собираются в большой system_prompt. Набор ресурсов задаётся для каждого эксперимента отдельно.
- **8.4 Логирование.** Вход пользователя, ответ агента, инструменты с аргументами и ресурсы пишутся в консоль и в `logs/agent.log`.

- **Ресурсы определяют, откуда берётся ответ.** Со всеми ресурсами агент ответил по справочнику без единого инструмента. Ресурс задаёт «свои» данные, поиск — чужие.
- **Middleware сработал до модели.** В эксперименте с персональными данными в модель ушло: «Моя почта [EMAIL], карта [CARD]. Сколько будет 7 + 8?». Попытка подменить инструкции и пустой запрос отклонены без обращения к модели и без расхода запросов.

## Ограничения и наблюдения

- **Сервер поиска заменён с DuckDuckGo на Tavily.** Локальный `duckduckgo-mcp-server` из этой сети результатов не давал: `html.duckduckgo.com` отвечал кодом HTTP 202 с пустой выдачей либо сбрасывал соединение, вариант с имитацией Chrome (`[browser]`) не помог. С ключом `TAVILY_API_KEY` агент подключается к удалённому серверу Tavily по streamable-http и получает инструменты `tavily_search` и `tavily_extract`; без ключа остаётся DuckDuckGo.
- **Соединение с удалённым сервером нестабильно.** В эксперименте без справочных материалов один вызов `tavily_search` оборвался сетевой ошибкой. `ToolErrorMiddleware` передал ошибку модели, агент повторил поиск и ответил.
- **Каждый вызов инструмента агентом запускает сервер заново.** Клиент `langchain-mcp-adapters` открывает новую stdio-сессию на каждую операцию: за полный прогон из 17 экспериментов сервер стартовал 13 раз, и вызов `add` из агента занимает около 1,6 с вместо 3 мс. Для агента с частыми вызовами выгоднее streamable-http или постоянная сессия.
- **Лимит токенов.** Модель тратит часть `max_tokens` на скрытые рассуждения: при лимите 1500 два ответа на исходный prompt пришли пустыми. Проверка показала `finish_reason=length`: из 1500 токенов 1072 ушло на рассуждения. Лимит поднят до 4000, после этого пустых ответов не было.
- **Ответы модели не детерминированы.** При повторном запуске формулировки будут другими, а погода — актуальной на момент запуска.
